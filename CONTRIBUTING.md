# Contributing

Last updated: 2026-08-07

---

## What this repository is

A public, sanitized portfolio documenting how KagePoint Systems is being designed and built.
It is a record of engineering reasoning, not a collaborative product.

## What contributions are welcome

- **Corrections** - factual errors, broken links, inaccurate technical statements
- **Clarity improvements** - places where the reasoning is hard to follow
- **Questions** - if a design decision seems wrong or under-explained, that is worth an issue.
  Well-argued disagreement about an architectural choice is genuinely useful

## What will not be accepted

- Requests to publish operational detail deliberately withheld (addresses, hostnames, zone
  identifiers, rule sets, evidence artifacts)
- Additions that claim capability or completion beyond what evidence supports
- Content from the separate ShadowForge creator/media domain
- Anything containing a credential, key, token, or personal data

## The honesty rule

This repository uses a five-level status vocabulary: **Planned, Documented, Implemented,
Tested, Validated**.

A contribution must not move something up that scale without evidence. If a section says
*Documented*, it means the design is written down and the implementation is **not** evidenced -
and that must stay accurate.

This matters more than it might sound. The credibility of the whole repository rests on its
status labels being trustworthy, including the unflattering ones.

## Reporting a security or privacy concern

Do **not** open a public issue. See [SECURITY.md](SECURITY.md).

## Process

1. Open an issue describing the change before submitting a substantial pull request
2. Keep pull requests focused on one thing
3. Match the existing tone: direct, specific, no marketing language
4. Confirm no sensitive information is included

## Code of conduct

Be accurate and be civil. Disagreement about technical decisions is welcome; assertions
presented as fact without support are not.
